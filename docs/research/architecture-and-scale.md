# Architecture and scale

Measured on the `v0.13` build, 2026-09-03, in Chromium at 390×844 against
a local static server. Every number here was taken rather than estimated;
where a number could not be taken, it says so.

This is the one arm of the v1 research round that is measurement instead
of literature. It exists because most of the other arms want to *add*
things — more question types, a richer event log, an offline mode — and
none of them can be costed honestly without knowing what the app already
weighs and where the weight is.

## What it costs to open the app today

| | |
| --- | --- |
| Requests | 27 |
| Transferred | 328.8 KB |
| Lesson list on screen | 1,034 ms |
| DOMContentLoaded | 379 ms |

Broken down: **142.9 KB of content JSON**, 94.7 KB of ES modules, 46.9 KB
of fonts, 39.5 KB of CSS, 4.8 KB of document.

That is a local server on a desktop. On a phone over Turkish mobile data
it is meaningfully worse, and the 1,034 ms figure is the one that would
move most.

## The finding that matters: the lesson list downloads 84× what it shows

The Eğitim index — the app's home screen — renders a list of 18 lessons.
Each row needs a category name, a one-line summary, an order number and
the topic it belongs to.

| | |
| --- | --- |
| Downloaded to render it | 141.4 KB (all three topic files) |
| Information actually on screen | 1.7 KB |
| Efficiency | **1.2%** |

It happens because `loadLessonsForTopics()` in `js/topics.js` fetches every
topic file in full, and a topic file carries its lessons *and* its 24
questions with their paragraphs, options, explanations and tips. The Test
tab does the same thing, for the same reason — it needs the category list.

Today this costs a second on a phone. It is worth fixing now anyway,
because the cost is **linear in content** and every other research arm in
this round is about to ask for more content:

| Content | List screen downloads | Needs |
| --- | --- | --- |
| Today (72 questions) | 141 KB | 1.7 KB |
| 5× | 707 KB | 8.5 KB |
| 10× | **1.38 MB** | 16.9 KB |

The exam arm of this round is likely to conclude that a credible
preparation app needs several times the current question count. If it
does, this stops being a performance note and becomes the thing that
decides whether the app is usable on a phone at all.

### The fix, and what it costs

Split what the index needs from what a lesson or a test needs.

`data/manifest.json` already carries per-topic metadata. Extend it with a
lesson index — `{ category, summary }` per lesson, in order — generated by
`tools/format-content.mjs` from the topic files rather than hand-authored,
so it cannot drift and no content author has to maintain it. Then:

- the Eğitim index and the Test tab load **only `manifest.json`**;
- a topic file is fetched when a lesson in it is opened, or when a test
  scoped to it is started;
- `js/topics.js` already caches per file, so nothing is fetched twice.

Cost: a generator step in the formatter, a validator rule that the index
matches the files, and a rewrite of `loadLessonsForTopics` into two
functions with different jobs. Perhaps half a day. It removes 141 KB and
roughly 600 ms from the first screen, and it keeps removing more as the
content grows.

The one thing to be careful about: the index screen currently shows a
lesson's *progress*, which is local, and its *step count*, which is not —
that second one already went away when lessons became scrolling pages, so
nothing on the index needs the question data any more. This is a change
the redesign made available; it was not possible before.

## There is no offline story

Measured:

- **Cold visit, offline: fails entirely.** `net::ERR_INTERNET_DISCONNECTED`,
  no page at all.
- **Visited once, then offline: the app works.** The lesson list renders.

The second result is not a feature. It is Chromium's HTTP cache happening
to still hold the files, and it holds them at the mercy of the cache's own
eviction and of whatever `Cache-Control` the host sends. It is not a
promise anybody can make to a user.

I could not measure GitHub Pages' actual response headers from this
environment — the sandbox's egress proxy returns 403 for `github.io`, so
the numbers I would otherwise quote here are not mine to quote. What
GitHub Pages sends, and how long it is good for, is worth establishing
from a primary source before designing around it.

Whether this matters is a real question rather than an obvious yes. A
student revising on a bus with no signal is a plausible user; a student
who only ever opens the app at a desk is equally plausible. The
release-readiness arm covers the service-worker mechanics; the question
for the owner is whether "works on the metro" is a v1 requirement or a
nice-to-have.

## The module graph is fine, and should be left alone

| Entry | Modules | Bytes |
| --- | --- | --- |
| `home.js` | 17 | 94.7 KB |
| `quiz.js` | 9 | 36.4 KB |
| `results.js` | 7 | 39.5 KB |

Seventeen requests for the home screen sounds like a lot and mostly is
not: they are parallel on HTTP/2, they cache independently, and the
largest is 24 KB. The obvious "fix" — bundling — costs the no-build-step
rule, which is the constraint holding this project's whole development
model together. Not worth it.

The one thing worth noting is that `js/education.js` is 24 KB and is
loaded by `home.js` on every visit, including a visit that only ever
touches the Test tab. A dynamic `import()` at the point the Eğitim route
is entered would defer it, at the cost of making the router async in a
place it currently is not. Small win, small cost, not urgent — and it is
worth measuring against the content fix above rather than instead of it,
since 24 KB is a sixth of what the topic files cost today.

## Storage has enormous headroom

After reading a whole lesson, the app has written **70 bytes**.

That is the entire footprint: one `englishPrep.lessonProgress` key. A full
test adds a history entry; the profile name adds a few dozen bytes more.

This matters for the learner-model arm, which is weighing whether a
per-item timestamped event log is affordable. Against a `localStorage`
budget measured in megabytes, at this rate, it plainly is — the constraint
on that design is not space. It is Safari's eviction of script-writable
storage, which is a durability question rather than a capacity one, and a
different arm's to answer.

## What I would build for v1

1. **The manifest lesson index**, generated by the formatter, so the home
   screen stops downloading the question bank. This is the only item here
   I would call necessary rather than desirable, and it gets *more*
   necessary the moment any other arm's content proposal is accepted.
2. **A decision about offline**, made deliberately. Either a service
   worker with a precache manifest — which is real work and adds a cache
   invalidation problem this project has never had — or an explicit note
   in the README that the app needs a connection. Both are defensible; an
   accidental half-offline that works until the browser evicts a file is
   not.

## What I would defer

- **Deferring `education.js` behind a dynamic import.** Real but small,
  and it should be measured after the content fix, not before.
- **Font subsetting further.** 46.9 KB is already inside the budget the
  design system set, and the remaining fat is the character coverage that
  keeps future Turkish content from falling back to a system face.
- **Any bundling, minification or build step.** Deferred permanently
  rather than temporarily.

## What I would refuse

**A service worker added for its own sake.** The pattern is cheap to copy
and expensive to own: every stale-cache bug in a static site is a service
worker deciding it knows better than the server, and this project has one
developer and no staging environment. If offline is a requirement, it
should be built with a versioned precache list generated by the same
tooling that generates the manifest index, and with a visible way for the
user to force an update. If offline is not a requirement, it should not be
there at all.

**Inlining the content into the HTML** to save requests. It would make the
first paint faster and make every content edit invalidate the whole
document, which is the wrong trade for a project whose content changes far
more often than its code.

## Open questions for the owner

- **Is "works without a connection" a v1 requirement?** Not "would it be
  nice" — would you use it on the metro, and would your friends? The
  honest answer decides whether a service worker is worth its cost.
- **How much content are we actually heading for?** The fix above matters
  at 5×; at 1× it is tidy engineering. The exam arm's answer to "how many
  questions does a credible app need" is what makes this urgent or not.
