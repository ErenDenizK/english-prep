# October 2026: research for a dark-first academic interface

**Access date: 3 October 2026. Scope: research and recommendations, not an implementation or usability-test report.**

This pass informs the requested premium academic refinement of the full English Prep app on mobile and desktop. It starts from `CLAUDE.md`, the current [Margin system](../margin-design-system.md), the existing [research record](../RESEARCH.md), and the supplied style exports. The product contains 10 topics, 60 continuously scrolling lessons, and 241 questions. The reading and testing modes, Turkish teaching/interface language, English examples, existing explanations, local progress, and question data remain the foundation.

The intended learner already functions in English but lacks some academic concepts and labels. A polished interface should help that learner find a distinction, read it, apply it, and understand feedback. It should not recast the app as beginner language instruction, a marketing landing page, or a proficiency certification.

## Method and strength of evidence

The evidence below was obtained from substantive public documents or implementation sources, not search snippets or a list of page titles. Official-site requests were attempted first. Where the network proxy blocked them, official public GitHub repositories supplied readable source documents. Each linked raw source below returned HTTP 200 and its relevant sections were read. Sources are mutable branches, so the access date matters.

Four kinds of evidence are deliberately separated:

1. **W3C normative criteria and their explanatory documents:** minimum accessibility obligations and specific testable behavior. AA and AAA are distinguished below.
2. **Google Material and Microsoft/Fluent guidance and source tokens:** evidence of a coherent, shipped design system. Native-platform measurements are not automatically web requirements.
3. **The Carpentries instructor guidance:** an evidence-informed teaching synthesis, applied here by inference. It is not a controlled English-preparation study.
4. **The user-supplied Home, Ventriloc, Monopo, and Raycast exports:** an aesthetic brief. They do not establish usability or learning outcomes, and their live websites were not inspected in this pass.

Apple HIG, NN/g, and two primary learning-paper endpoints could not be read because of proxy restrictions. They are listed in the access record and are **not** used to substantiate recommendations. Reading the Apple/Swift DocC repository README did not amount to consulting HIG, so it is not included as evidence.

## Findings that should shape the implementation

- **Dark-first means a fully designed dark experience, not dim text.** Define semantic surface, text, boundary, focus, and feedback pairs; retain an effective light option and respect an explicit saved preference. The consulted evidence does not show that dark mode universally improves reading.
- **The article is the main product object.** Give learning prose a stable measure and generous leading; keep curriculum controls visually distinct from English examples and explanations. Extra desktop width should make related information adjacent, not stretch articles across the screen.
- **A type scale is a set of complete roles.** Family, weight, size, leading, and context belong together. A large title cannot compensate for undersized descriptions or ambiguous control labels.
- **Hierarchy should survive without special effects.** Headings, grouping, alignment, spacing, and clear actions must work before glow, blur, motion, and artwork are considered.
- **The fixed shell creates concrete accessibility obligations.** Focus must not disappear behind the header or footer; text must reflow at 320 CSS pixels and tolerate spacing overrides; zoom and short windows need real tests.
- **Preserve meaningful interaction.** Immediate corrective feedback, optional checks, article continuation, category practice, mistake review, and backup are valuable source features. Research does not justify replacing them with a decorative dashboard or a forced onboarding flow.

## Prioritized decisions for tokens, components, and flows

### P0 — protect reading, meaning, and access

1. **Define complete text roles and audit them in context.** For the refinement, start with 17–18px Turkish article prose, 19–22px English examples/questions, 16px explanation prose, and at least 13–14px essential UI labels. Treat these as implementation candidates to measure, not universal scientific minima. Reserve smaller type for supplementary metadata. Keep body leading approximately 1.65–1.9 and test real Turkish/English lines before tightening it. Sources: S1, S5, A1, A4, A8.
2. **Use one dark neutral hierarchy and paired semantic colors.** Page, content surface, selected/recessed surface, and overlay should be distinguishable without relying on glow. Assign `ink`, `ink-2`, `edge`, `focus`, `accent/on-accent`, and semantic feedback pairs explicitly. Preserve a light counterpart and saved preferences. Sources: S2, S7, A1, A2, A10.
3. **Make curriculum rows more useful than decorative cards.** One clear title, one concise purpose, a real progress/count signal when useful, and an obvious destination. Do not hide a primary title behind decorative numbering or a badge. Sources: S4, S9, L2.
4. **Keep articles continuous and available.** No modal or required answer should block the first paragraph. Pretests remain optional; inline checks remain unscored and do not gate completion. Reading resume remains grounded in source progress. This combines the user's product constraint with L1/L2; it is not an independently validated optimal pedagogy.
5. **Preserve the answer-feedback loop.** A chosen answer commits immediately; existing rationale, selected-option note, and transferable rule stay legible. State changes must not move another answer under a pending tap or hide the next action. Do not replace explanations with success animations. Sources: L1, L2, A7, A10.
6. **Validate the fixed frame under stress.** Test keyboard focus, 320px reflow, spacing overrides, large zoom, long labels, short landscape windows, modal opening, and on-screen keyboard use. Set appropriate content padding/scroll padding and use minimum rather than rigid content heights. Sources: A3–A7.

### P1 — make the system feel deliberate

7. **Use a small, named spacing and shape vocabulary.** Related label/control spacing should be smaller than section separation. Consistent corners and boundaries should explain object type; avoid repeated nested frames. S4 supports consistency, not a mandate for a specific 8px grid.
8. **Make desktop genuinely useful within the source architecture.** Preserve meaningful wide splits and a stable reading column. Use desktop space for curriculum context, topic overview, and results/review adjacency; keep articles/quizzes focused. Sources: S6, A3, A8; the no-reader-pane rule is also an explicit product constraint.
9. **Give components a complete state set.** Specify default, hover where applicable, pressed, selected/current, focused, disabled, pending, empty, and error states. Check dark/light, pointer/keyboard, and forced-color behavior. Not every component needs every state, but no required state should be invented ad hoc in a screen.
10. **Constrain motion by purpose.** Use short state transitions and retain immediate feedback even when movement is disabled. No loading illusion, card entrance, or count-up should postpone useful information. Sources: S8 and A9.
11. **Keep navigation labels and context explicit.** Preserve Eğitim/Test and header Profil; show where a lesson lives and how to leave it. Results should reach the relevant category or lesson without navigating up and down the entire hierarchy. Sources: S3 and S9.

### P2 — refinements only after functional review

12. Reconsider purely decorative marks, micro-labels, and large introductory titles only after curriculum density, article measure, contrast, and actions pass inspection. The supplied references justify a restrained visual character, not additional hero artwork.
13. Improve empty, partial, loading, and unavailable-offline states with specific next actions. Distinguish no saved history from a zero score, no search results from unavailable data, and an absent offline lesson from a broken entire app.
14. Keep product metrics literal: available material, actual reading progress, recorded accuracy, and the source's evidence thresholds. Avoid unvalidated mastery badges, invented streaks, or exam-readiness percentages.

## Four distinct review passes and required evidence

This is the proposed review protocol. Completion must be recorded by the implementation owner with actual findings and outcomes; this research document does not claim the passes have already happened.

| Pass | Review question | Minimum evidence and useful corrections |
| --- | --- | --- |
| **1. Structure and reading hierarchy** | Does each screen make its task and next action obvious without decorative explanation? | Review actual dark-mode screenshots at 320px, ordinary mobile width, and desktop: Eğitim, topic overview, an article, Test setup, one answered question, results, Profil. Trace the reading/practice/return flow. Correct unclear labels, competing actions, overlong introductions, weak lesson context, and density problems before polishing colors. |
| **2. Type, color, and component consistency** | Do actual rendered roles, colors, boundaries, and states form one system? | Measure computed family/size/weight/leading and foreground/background pairs; inspect representative Turkish text, English sentences, long titles, selected options, and feedback. Review both themes, cached/system-font fallback, and responsive widths. Compare with token definitions rather than just checking screenshots by eye. |
| **3. Interaction and accessibility** | Can a keyboard/touch user operate every core flow without losing context or content? | Exercise Back/routing, search, collapsed disclosures, optional checks, all test modes, answer feedback, review links, profile, and backup. Test full keyboard traversal, visible/unobscured focus, 320px reflow, spacing overrides, reduced motion, and dialog recovery. Record failures rather than declaring broad conformance from an automated score. |
| **4. Preservation, offline behavior, and release** | Does the final artifact still contain the same learning product and work when installed or revisited? | Verify content/ID equivalence, stored-progress compatibility, original-version availability, scoped service-worker lifecycle and offline assets/content. Run the repository's required checks and real-browser journeys against the final revision. Inspect the actual GitHub Pages result after the authorized deployment, including a returning/offline path; a push is not evidence that the published app has refreshed. |

A four-pass process should produce four sets of observations, corrections, and verification evidence. Record the distinct findings from each pass and rerun the checks affected by its corrections. The preserved original provides a comparison artifact; a usability improvement still needs evidence.

## Remaining uncertainty

There is no new user sample, controlled readability experiment, screen-reader study, or learning-outcome measurement behind these recommendations. Dark priority and the aesthetic direction are user preferences. Font pairing, reading size, spacing, and density are design hypotheses that should be checked with the intended learners. Current public guidance supports coherent roles and accessible behavior; it does not establish that a particular visual style or palette produces better learning outcomes.

The next user-research step is small and concrete: observe English-capable prep students locate an unfamiliar grammar label, read the corresponding distinction, explain why an answer fits, resume after interruption, and interpret their progress. That would test the product's actual purpose more directly than asking whether a screenshot looks premium.
