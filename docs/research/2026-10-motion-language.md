# A motion language for English Prep

Research date: **4 October 2026**. Scope: the owner's v0.68 request for a more considered application feel, a short animated introduction, and a living cherry/sakura atmosphere on every screen. This is research and an implementation contract; it does not claim that a proposal has already passed device, performance or usability testing.

## Finding

The app needs different responses for different kinds of action, rather than more animation everywhere. A learner's answer, text entry and selected state should be committed immediately. A menu or page transition can explain where the next surface came from. Finishing a lesson or test can receive one short local emphasis. Background movement is decorative identity and needs a persistent off control. It must never be mistaken for loading, progress or a learning reward.

The earlier ADR 006 deliberately selected a finite 3.6-second atmosphere and hid it behind opaque reader/quiz canvases. The owner's new request changes both decisions: continuous movement, visible on the reading and quiz screens too. This requires an accessible stop mechanism, measured maximum color compositing, and a background implementation shared by every entry document. It does not justify animated text, delayed answers, confetti, or a moving reading column.

## Current application audit

The v0.67 source currently flattens `.animate-in` to a 180 ms opacity reveal; all child stagger is disabled. Several legacy spring names resolve to one easing and 180–220 ms durations. Answer colors transition for 180 ms, while answer pop/shake effects are correctly suppressed. The results figure still counts from zero for 700 ms; this is a different numerical state from the final accessible score and creates extra movement without explaining anything. The lesson reading progress animates `width`, which can lag a scroll-derived value. The background has a single finite settle and the reading/quiz scroll canvas is opaque, explaining why the atmosphere disappears there.

The proposal preserves the good parts: immediate answer commitment, stable option geometry, no wrong-answer shaking, no staggered article paragraphs, and a fixed action bar. It gives the remaining transitions a clear role and removes decorative numeric counting. Imported but unused celebration code is not a reason to revive confetti.

## Proposed timing and action matrix

These exact values are **application design choices**, informed by the ranges above. They are not a timing threshold prescribed by WCAG or a measured universal preference.

Use four shared duration roles: **100 ms control**, **180 ms reveal**, **220 ms navigation**, **420 ms milestone**. Use `cubic-bezier(0.2, 0, 0, 1)` for entering/settling UI; use `cubic-bezier(0.3, 0, 1, 1)` only if a real exit must animate; use linear for short opacity feedback. Ambient periods are a separate system, not extra control timing roles. Avoid overshoot/bounce for the academic reading interface.

| Interaction | State and access response | Optional visible treatment | Do not do |
| --- | --- | --- | --- |
| Type a name, move a caret, toggle a setting, keyboard focus | Immediate value, focus and ARIA update | A control's nonessential background may settle in 100 ms; focus outline appears immediately | Animate text, delay form updates, fade focus into view |
| Press a primary/secondary button | Activate immediately on the normal click/keyboard event | Pointer press scale `0.985`, at most 100 ms; return at release | Delay the handler, scale a multiline answer, use pointer-only behavior as the sole response |
| Select a test/check answer | Record answer and disable repeat scoring immediately; announce outcome immediately | Stable marker/short label reveal in 180 ms; low-area state tint transition | Shake wrong answers, bounce the sentence, shift the option grid, wait for animation before revealing explanation |
| Open a combobox/menu or dialog | Open and manage focus immediately | 180 ms opacity plus at most 4 px translation | Scale the whole viewport; leave an invisible closing popup intercepting events |
| Switch Eğitim / Test | Change route and selected tab immediately | Indicator travels in 180–220 ms; incoming content fades in 180 ms | Queue transitions or replay a stagger across all rows |
| Open/back from topic or lesson | Resolve route and scroll restoration immediately | At most 220 ms opacity with 4 px maximum entrance movement; restored reading position can simply appear | Slide long prose from off screen; smooth-scroll a restored position; combine two nested page fades |
| Onboarding next/back | Advance only on user input; update step text and focus immediately | 220 ms page cue from `+8px` forward / `−8px` back; demo elements may reveal once with 40 ms spacing and a total under 420 ms | Auto-advance, animate the whole text through a large distance, replay a looping fake quiz |
| Scroll-derived reading progress | Directly show the current fraction | None; transform-based fill avoids layout work | Apply easing that trails a finger, count percentages or reset the bar to zero on return |
| Completed lesson/test | Show final real count and next useful action immediately | One 420 ms local check/progress emphasis; optional icon scale `0.94 → 1` with no bounce | Count score from zero, pulse forever, celebrate only high scores with a noisy overlay |
| Error, destructive action, unavailable feature | Show a clear explanation immediately | None required | Cheerful reward motion, shake the whole form, color-only feedback |
| About feature switch / media preview | User-controlled activation, real selected state | 180–220 ms local reveal | Auto-playing carousel; hide content until an intersection animation runs |

The completion treatment acknowledges **finishing the study action**, not an arbitrary score threshold. The final score remains readable from the first frame. It is acceptable to omit an effect where the existing component cannot safely animate without changing geometry.

Motion must be interruptible. Repeated navigation must not queue delayed DOM mutations. Hidden routes must not keep animations or timeouts alive. For native View Transitions, either use that one transition or the incoming component animation; avoid multiplying both. CSS transitions should name the intended properties, never `all`.

## Living atmosphere across the app

Use three low-chroma cherry, sakura and complementary lilac gradient fields drawn as ordinary fixed decoration. They can occupy different edges and heights, so identity survives on Education, Test, reader, quiz, results and Profile, rather than residing only behind the home hero. Use the same shared implementation for all documents; the About page can reuse it.

The proposed fields animate **transform and opacity only**. Each field keeps its actual gradient colors fixed. Their relative positions and opacity make the combined hue gently evolve without animating gradient stops, `filter`, `hue-rotate`, blur, background size, or text colors. Suggested periods are **28, 34 and 42 seconds**, alternating ease-in-out, with distinct starting phases. Travel stays within **12–20 px**, scale within **1–1.04**, and field opacity within **0.72–1**. These are initial design bounds to assess, not observed battery-safe values.

Keep field bounds reasonably small, for example `clamp(240px, 55vmin, 520px)`, with centers near different viewport edges. Do not make three enormous, blurred, promoted full-screen surfaces. The fields have no pointer events, no accessible content and no foreground stacking over text. The brand dot can use a static related color; it does not need another loop. Avoid permanent `will-change` on all app objects.

To remain visible on a phone reader, the entire scroll region cannot hide the atmosphere behind an opaque fill. Instead, use a bounded low-alpha page background under the reading measure, opaque action/answer/card surfaces where applicable, and a **worst-case triple-overlap contrast calculation beneath unboxed text**. The center should remain quiet even at the brightest phase. Every field's maximum gradient alpha is measured with its animated opacity at 1; all stacking orders must be covered, since three fields can overlap differently in responsive layouts. No unmeasured blend mode or extra glow layer may be added after that measurement. The palette study owns the final colors and alpha ceilings; this report does not choose unverified hex/alpha values.

The choice supersedes ADR 006's full opaque reader background, but keeps its reason: decoration must not compromise the material. A screenshot at the dimmest animation phase is not evidence that the brightest phase is safe. Text/readability checks must cover both extremes and both themes. Forced-colors and print omit the fields entirely. Reduced motion keeps a static composition, so turning motion off does not erase the new identity.

## One persistent motion preference, reachable everywhere

[WCAG 2.2.2 Pause, Stop, Hide](https://raw.githubusercontent.com/w3c/wcag/main/understanding/20/pause-stop-hide.html) requires a pause/stop/hide mechanism for relevant automatically starting movement lasting over five seconds alongside other content. Its guidance recommends a single mechanism when multiple elements move. [WCAG 2.3.3 Animation from Interactions](https://raw.githubusercontent.com/w3c/wcag/main/understanding/21/animation-from-interactions.html), an AAA criterion, supports disabling nonessential interaction movement. Neither reduced-motion detection alone nor pausing only while a button remains focused is an adequate product control for the proposed continuous decoration.

Provide **one stored preference** with a compact 44×44 px pause/resume control in the shared header and an equivalent **Hareket** setting in Profile. Those are two ways to edit one setting, not independent ambient and transition preferences. A reader or quiz user must be able to stop movement without leaving their work. The tooltip/accessibility label should explain the action, e.g. “Hareketi durdur” / “Hareketi aç”; the Profile description can say “Arka plan ışığı ve geçiş animasyonları.” A consistent pressed state should expose the current preference. Do not introduce a settings dashboard for timing, colors or intensity.

**Measured narrow-screen constraint:** at a 320 px viewport, the current reader header's inner width is 288 px. The existing “Dersler” lead measures 101.14 px, the truncated lesson title 132.13 px, and `2 / 6` counter 30.73 px. A 44 px control plus an 8 px gap leaves roughly 80 px for the title. Full lesson text already appears in the content heading, so header truncation is possible, but a compact icon-only back control with a preserved accessible name at the narrowest breakpoint offers more room. Verify this choice with text enlargement, long topic names and three-digit counters; do not solve it by reducing touch targets or shrinking text. Home also has the Profile button, so its two controls need the same test.

The effective motion state is enabled only when the stored preference permits it **and** the OS does not request reduced motion. An explicit in-app “on” must not override the system's reduction request. Reflect that state clearly; do not display a misleading active switch while nothing can move. Listen for a mid-session OS preference change. Local storage failure should not prevent rendering or toggling the current session's preference.

Use a shared early-initialized module and root state such as `data-motion="full|reduced"`. All CSS transitions/animations and JS effects must obey it, including existing `motionWelcome()` callers, tutorial cues, progress effects and About media. Stop any running nonessential JS animation immediately when the setting changes; simply gating its next creation is insufficient. For video demonstrations, retain native controls and a poster; a decorative GIF cannot provide the same pause behavior.

Use `document.visibilitychange` to pause the ambient CSS animations while hidden and resume only if both the user and OS still allow motion. [MDN's Page Visibility guidance](https://raw.githubusercontent.com/mdn/content/main/files/en-us/web/api/page_visibility_api/index.md) explicitly supports suspending unnecessary work; browser timer throttling is not a substitute for the application policy. Do not reset the aurora on every route or scroll event.

## Verification contract

[MDN's rendering guide](https://raw.githubusercontent.com/mdn/content/main/files/en-us/web/performance/guides/animation_performance_and_frame_rate/index.md) explains why geometry changes can cause layout and repaint, while transform/opacity can be composited when separately layered. It does not guarantee 60 fps or negligible power consumption for every CSS effect. A slow loop still schedules work; only a trace and device measurement can establish its cost.

Before publishing:

1. On 320, 390, 768 and 1440 px screens, inspect answer/next-button geometry before and after a wrong and a correct answer. No answer line rewrap or control displacement caused by animation is acceptable.
2. Verify a response's saved state and live announcement exist immediately, independently of animation completion. Verify rapid tab/tour navigation yields the latest requested state.
3. Check visible atmosphere on every route and entry HTML, including the reader and quiz; measure foreground pairs under the maximum three-field overlap, not just opaque cards. Inspect both static and animated views with actual long teaching text.
4. Test header pause by keyboard/touch while midway through a lesson and unanswered quiz; the route, scroll position and answer state must remain unchanged. Confirm preference persistence across document navigation and the matching Profile control.
5. Test OS reduced motion at startup and changed mid-session, explicit in-app off, hidden-tab pause/resume, forced colors and printing. No active ambient or JS decorative loop should remain when motion is off.
6. Record a browser performance trace of a settled reading screen with aura on and off. Identify any recurring layout/paint caused by the effect and bound layer size. Report the actual environment and observations; do not infer phone battery or universal 60 fps from desktop headless Chromium.
7. Capture at least one short manual motion review at a realistic phone viewport. Numeric passing checks do not establish that the effect feels calm or refined; if it competes with reading, reduce alpha/travel before adding complexity.

The deliberate result is a reliable, immediate study tool with a recognizable ambient identity. Richness comes from consistent relationships between action, response, color and space—not from making every element perform.
