# v0.70: expressive motion with immediate application behavior

Research and source inspection: **4 October 2026, Türkiye time**. This is a UI
revision; lesson text, question text, explanations and learning rules are outside
its scope. It responds to the owner's observation that v0.69 was too restrained,
especially in the introduction, completion screens, Profile and mobile About.

## Evidence, and what was not observed

The following **official implementation sources were retrieved and read**. Token
values describe those systems; they are not a usability study of English Prep.

1. [Carbon motion token source](https://github.com/carbon-design-system/carbon/blob/main/packages/motion/src/dtcg/motion.json)
   explicitly assigns 70/110 ms to small interactions, 150/240 ms to moderate
   movements and 400/700 ms to deliberate transitions. It distinguishes
   **productive** and **expressive** curves. Its descriptions associate the
   slowest role with large hero transitions rather than ordinary button input.
   [The consuming TypeScript](https://github.com/carbon-design-system/carbon/blob/main/packages/motion/src/tokens.ts)
   preserves those separate curve modes instead of selecting one universal ease.
2. [Material Web motion v0.192](https://github.com/material-components/material-web/blob/main/tokens/versions/v0_192/_md-sys-motion.scss)
   provides 50–200 ms short, 250–400 ms medium, 450–600 ms long and 700–1000 ms
   extra-long roles. Standard and emphasized acceleration/deceleration are
   separate. The thin forwarding file is not itself timing evidence; this link
   is the actual generated token implementation.
3. [Material Android expressive spring tokens](https://github.com/material-components/material-components-android/blob/master/lib/java/com/google/android/material/motion/res/values/tokens.xml)
   separate **spatial** from **effects** springs. Expressive spatial damping is
   0.6 for fast and 0.8 for default/slow, while effects use damping 1. Standard
   spatial damping is 0.9. This is evidence for selecting different movement
   characteristics by object/property, not for bouncing color or every label.
   Android physical parameters cannot simply be copied into CSS milliseconds.
4. [Fluent curves](https://github.com/microsoft/fluentui/blob/master/packages/tokens/src/global/curves.ts)
   and [duration tokens](https://github.com/microsoft/fluentui/blob/master/packages/tokens/src/global/durations.ts)
   supply distinct acceleration/deceleration curves and a 50–500 ms scale.
   A professional productivity interface can therefore have multiple motion
   roles without treating every element identically.
5. [MDN `Element.animate()`](https://developer.mozilla.org/en-US/docs/Web/API/Element/animate)
   and [MDN `Animation.cancel()`](https://developer.mozilla.org/en-US/docs/Web/API/Animation/cancel)
   support finite, independently cancellable browser effects. Cancel removes
   the effect and rejects an active `finished` promise with `AbortError`;
   cleanup must handle fulfillment and rejection. Their official MDN GitHub
   document sources were retrieved.
6. [MDN `linear()`](https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Values/easing-function/linear)
   explains piecewise easing and progress values outside 0–1. It is a possible
   spring approximation technique. This release instead uses three explicit
   WAAPI keyframes, avoiding another browser support condition and an idle
   JavaScript spring solver. These authored settles are **spring-like**, not
   a physical simulation or copied Material springs.

The public Carbon guideline page, Linear features site and Raycast home page
were attempted but the network returned **403**. No current live visual timing,
interaction measurement or competitor screenshots are claimed for them. Some
initially guessed source paths returned 404; only successfully retrieved source
files appear as evidence above. In particular, familiar product names are not
used to justify invented measurements.

## Diagnosis of the application

Before editing, the actual `js/interactions.js` had four roles:
100/160/220/360 ms. Most effects moved only 3–6 px or scaled .96→1; nearly every
role used the same deceleration. `scene` was a single 6 px slide at 220 ms.
There was no shared composition API. CSS similarly limited the selected glyph
and answer symbol to tiny reveals. This made the controls clear but gave almost
no hierarchy between opening a menu and completing a whole study session.

The useful pieces remain: immediate native state/focus, a cancellation registry,
OS and stored motion preferences, hidden-page handling, no recurrent JavaScript
animation loop and a stable reading surface. The revision increases expressive
range and orchestrates related shapes instead of adding delay to application
logic or randomly lengthening every transition.

## Product decisions

These are reasoned design choices for this app, not universal thresholds.

| Role | Duration | Application meaning |
| --- | ---: | --- |
| Control | 100 ms | A press responds now; short surface/arrow feedback. |
| Reveal | 220 ms | Menus, small content additions and short section cues. |
| Route | 360 ms | A new context or small glyph settles into place. |
| Scene | 560 ms | An introduction step, Profile section or product illustration. |
| Complete | 720 ms | A completion symbol, deliberate connector trace or final progress fill. |
| Story | 900 ms | Larger decorative artwork in the introduction/portfolio. |

The exact scale is smaller than Material's entire token catalog and broader than
v0.69. The longer roles are **presentation**, never a wait before a user can
continue. Staggers are capped at 180 ms; even the largest composition ends within
1080 ms. No task is completed, score calculated, storage written, button enabled
or focus assigned in an animation completion callback.

- **Readable surfaces** use fully opaque text and bounded translation. Ordinary
  reveal moves 8 px; a route or introduction title moves at most 12 px. Prose
  never scales, rotates, counts up, breaks into animated letters or springs.
- **Decorative artwork** may travel 20–24 px and settle with a small overshoot.
  The shared completion preset peaks at scale 1.045. These are explicit three-frame
  sequences; they settle completely and have no idle work.
- **Drawing communicates the route**: normalized decorative SVG paths trace the
  article/check/review relationship. The selected step, explanation and action
  remain available before the path has finished drawing.
- **A result is immediate**: actual score and literal status do not animate
  through false intermediate values. A separate glyph or line carries the
  longer conclusion. Incorrect answers never shake or suggest punishment.
- **Pointer response is a second layer**: fine-pointer artwork has bounded tilt
  and light position; touch and keyboard have complete native controls and the
  same finite action-triggered scenes. Reading text never follows the pointer.
- **Repeated actions replace motion**: fast Next/Back, scene choices and menu
  close cancel preceding effects. Enabling motion does not replay old events.
- **Search, typing, restored reading position and explanation text stay stable**.
  This is a reading/test app; increased motion must not become an obstacle to
  studying or make focus rings arrive late.

## Shared implementation

```js
animateElement(element, kind, { channel, direction, delay });
animateSequence([
  { element: heading, kind: "onboard", at: 0 },
  { element: illustration, kind: "scene", at: 80 },
  { element: connector, kind: "draw", at: 160 },
], { channel: "introduction", direction: "forward" });
cancelAnimationsWithin(outgoingContainer);
```

`animateSequence` returns the actual `Animation[]`; it schedules no application
callbacks or timers. The `at` value is a browser animation delay clamped to
0–180 ms. A delayed effect uses `fill: backwards`, keeping its first decorative
frame until it starts; text remains fully opaque. Every effect returns to the
authored final CSS after completion or cancellation, with no `fill: forwards`
state retained. Missing/unsupported/detached hosts immediately retain the static
presentation. Callers release outgoing entries before replacing a scene.

Additional presets include `mark`, `dialog`, `route`, `onboard`, `scene`,
`complete`, `story`, `draw`, `progress` and `rule`. A drawn path must have
`pathLength="1"` and a complete static stroke. A progress/rule wrapper sets its
own transform origin and final width; only its decoration scales, never a label
or the actual numeric value. Existing `animateElement` callers remain valid.

One owner per target is essential: do not apply CSS entry keyframes to the same
node that a WAAPI composition controls. Finite CSS glyph effects and ordinary
hover states remain appropriate elsewhere. Pointer scenery retains one rAF per
input burst, no idle rAF, no capture and no scroll interception. New transitions
introduce neither a runtime dependency nor a build step.

## Verification

`node --test tests/interactions.test.js tests/motion.test.js` passed **17 tests**
after the shared API change. Focused assertions cover:

- replacing an active channel, releasing completed effects and cancellation;
- off/OS-reduced/hidden/pagehide cancellation and no stale replay;
- sequence delays capped at 180 ms, durations and final frames;
- immediate text state, fully opaque text and no recurrent rAF from sequences;
- input settling an active ancestor without cancelling independent artwork;
- decorative draw/progress endings and CSS duration token resolution;
- unsupported/detached nodes and pointer burst coalescing/bounds/cleanup.

Browser integration, responsive geometry and actual scene coverage belong to the
release's UI verification record. Unit tests do not certify smoothness on every
physical phone, thermal condition or Safari version.


## Independent integration pass

A local Chromium audit used the production-style `/english-prep/` path at
320, 390 and 1440 px. `Element.animate` was instrumented before application
modules loaded; values below come from created browser effects, not merely the
duration token table. This instrumentation was temporary under `/tmp`, not
shipped code.

- First introduction scene: maximum end time **720 ms**; optional-name/brand
  conclusion: **880 ms** including the delayed dot. At 320/390/1440, initial
  effects had finished after the observation window, without horizontal
  overflow or uncaught errors. SVG groups used `transform-box: fill-box` and
  local central origins, avoiding unintended drift around the SVG coordinate
  system's origin.
- About hero: **900 ms** maximum end time, with the connector ending at 880 ms.
  Five rapid study-stage choices cancelled the previous twelve effects and left
  only the latest three active. Switching motion off made all fifteen idle
  immediately while retaining the final selected copy.
- Settled introduction/About: **0 extra requested animation frames over 500 ms**;
  settled article reader: **0 over 750 ms**. This demonstrates absence of a new
  idle JavaScript loop in those observations; it is not a GPU/energy benchmark
  or a guaranteed device frame rate. The three existing CSS atmospheric fields
  still animate when enabled.
- A synthetic visibility-change test immediately cancelled active WAAPI effects
  and put all three CSS atmosphere fields into `paused`. This is an event-path
  check, not physical-device background testing.

Two integration findings were corrected instead of weakening tests:

1. Scaling the popup to .98 caused a 1–3 px last-option clipping regression in
   short landscape menus because transformed rectangles were compared with
   unscaled scroll metrics. The menu now translates without scaling. Input
   (`pointerdown`/`focusin`) also settles an active target/ancestor before focus
   scrolling or popup placement reads its geometry. Independent artwork is not
   interrupted. The focused unit suite includes both constraints, and the existing
   `EditorialBrowserTests.test_count_popup_keyboard_visibility_in_short_viewports`
   browser regression passed after the corrections.
2. About's disclosure query initially selected an earlier label paragraph inside
   the summary instead of the feature body. It now explicitly prefers the
   feature body, falling back to a direct paragraph for engineering/FAQ details;
   the About browser test verifies the intended body receives the effect.
