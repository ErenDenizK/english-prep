# v0.68 motion engineering review

Reviewed 4 October 2026 against the working v0.68 files. This is a focused
engineering check, not a claim of physical iPhone testing, battery efficiency,
universal frame rate or measured learning benefit.

## Found and corrected

The route implementation initially combined native `startViewTransition()` with
the existing `.animate-in` CSS cue. In Chromium, one Education → Test navigation
delayed the DOM update by 17.7 ms and kept the native transition alive for about
299.6 ms. The snapshot overlay had `pointer-events: auto`; hit-testing in the
navigation area returned the root HTML element. The animation inventory showed
the CSS entrance and five native view-transition pseudo animations together.

The final implementation commits the route synchronously and keeps the finite
CSS entrance. A second browser observation confirmed that, in the same
`hashchange` dispatch after the app's handler, Test was visible, focus was on
`view-test`, and hit-testing reached the Test tab. There were zero native
transition calls and zero view-transition pseudo animations. The observed
handler-to-verification interval was 9.3 ms, including the verification's layout
read; this is not a cross-device latency benchmark.

## State and lifecycle checks

| Check | Observed result |
| --- | --- |
| Eight visits to the introduction and back | Document-level motion-related listener counts stayed constant: one `visibilitychange`, zero `motion:change` listeners in the app document. |
| Ambient initialization | One `.ambient` container with three fields; repeated initialization did not duplicate it. |
| Pause while reading | At scroll position 1800 px, pressing the header control left the route and scroll position unchanged, preserved button focus, and paused all three fields. |
| App → About → app preference | The stored off preference was respected in both directions. |
| About gallery action | The image source/selection changed immediately; a single finite image reveal was present immediately after the click. |
| OS reduced-motion change during the gallery reveal | The JavaScript reveal was cancelled and no animation remained running. |
| Visibility-handler test | With `document.hidden` deliberately overridden and a `visibilitychange` event dispatched, all three fields paused and the JavaScript gallery reveal was cancelled. This tests the handler, not an actual mobile operating-system background lifecycle. |
| Stable control semantics | The control's accessible name remains “Hareket”; `aria-pressed` reflects effective motion. An OS reduction exposes `aria-disabled="true"` and an explanatory title. |
| Page errors in the reviewed flows | None observed. |

The visibility-handler observation also contained four short CSS button
color/background transitions that were still finishing. Those were not gallery
JavaScript effects or perpetual loops; the observation must not be described as
“every CSS transition stops instantly when the tab is hidden.” Explicit off and
OS reduction disable the CSS transitions as well.

Source review found no new continuously scheduled JavaScript animation loop.
The aura is handled by CSS transform/opacity animation. The reader's existing
`requestAnimationFrame` is scheduled by scroll activity, not as an idle loop.
The compatibility `countUp()` helper now removes its event listener when it
finishes or is interrupted, and current results no longer call it. The old
confetti module is not imported by the application entries. About's finite
Web Animations are kept in a set and removed on finish/cancel; motion/visibility
changes cancel those active effects. Detached toggle buttons are not held in a
module-level collection: connected controls are queried when state changes.

## Bounded performance observation

Environment: Linux headless Chromium **151.0.7922.173**, **390 × 844 CSS px**,
device scale factor **1**, no CPU throttling, local static server, service worker
blocked for the observation. Page: the settled Unless lesson. Each observation
lasted approximately four seconds after initial rendering/transition work had
finished. Chrome DevTools Protocol `Performance` metrics and `devtools.timeline`
events were recorded.

| Four-second settled-reader window | Aurora running | Aurora paused |
| --- | ---: | ---: |
| Layout count delta | 0 | 0 |
| Style recalculation count delta | 0 | 0 |
| Trace Paint events | 0 | 0 |
| Trace animation-frame callbacks | 0 | 0 |
| JavaScript duration delta | 0 ms | 0 ms |
| Main-thread task duration delta | 6.031 ms | 0.647 ms |

This supports the narrow finding that the settled effect did not trigger
recurring main-thread layout, paint or JavaScript callbacks in that observation.
It does **not** show zero GPU work, zero energy cost or guaranteed 60 fps.
The layer tree contained three drawn atmospheric layers of **438 × 892 px**,
matching the viewport plus the 24 px inset on each side. They are viewport-sized
composited fields, not the smaller field dimensions suggested as an early option
in the research. The final implementation uses their wider coverage to maintain
the requested atmosphere across the reading screen; layer cost remains a reason
to keep only three, avoid blur/filter animation, pause when hidden and retain
the user control.

Session raw observations: `/tmp/ep68-motion-audit/performance.json`,
`behavior.json`, `final-route.json`. These temporary paths are local evidence for
the session; the methods and measured results above are the durable record.
The six state unit tests are in `tests/motion.test.js`; broader browser coverage
is maintained by the v0.68 regression pass.
